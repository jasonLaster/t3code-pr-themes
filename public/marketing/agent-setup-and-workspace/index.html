Part 1

Let your agent set up T3 Code

T3 Code is open source, so the agent you're already coding with knows how it works. And because the app is built around tools agents can drive, there's no reason your agent can't configure T3 Code exactly the way you like it.

The big missing piece was settings. An agent could only change 5 of the 88. So if I asked it to prefix my branches with jl/ or stop keeping my Mac awake, it just couldn't. That's what headless settings fixes.

thread · laptop · Full access
Prefix my new branches with jl/, and stop keeping my Mac awake while agents work.
t3_settings_read branchPrefix, preventSleep writewrite
t3_settings_update { branchPrefix: "jl/", preventSleep: false } → saved
Done. New worktree branches start with jl/, and T3 Code won't keep your Mac awake during turns anymore.
Also let agents use the browser by default.
t3_settings_read browserAccess user
That one widens what agents can do, so it's your call. You'll find it under Settings → Agents.

Which settings can an agent touch?

Every setting gets an access level, and the type system enforces it. If someone adds a new setting and doesn't decide whether agents can change it, typecheck fails.

Anything secret, anything that widens what agents can do, and anything that deletes files or runs later stays with you.

Where I want this to go

Settings are step one. I went through every action in web, desktop and mobile, and every endpoint behind them. About a quarter to a third already have a tool. The rest sort into four buckets, and the last three can share one request card instead of a new UI for each.

Agent just does it

  • Terminals and scripts
  • Diffs, commit, pull
  • PR dashboard, usage
  • Preview and device controls
  • Keybindings, project settings

Needs your OK

  • Widen permissions
  • Delete a thread
  • Roll back a checkpoint
  • Remove a worktree
  • Sharing, server updates

Needs your input

  • Pairing codes
  • SSH passwords
  • Provider and forge sign-ins

Only your app

  • Add an SSH or T3 Connect env
  • Port forwarding, app updates
  • On-device preferences
#41091 open

Headless settings: agents can read and change environment settings

Two new tools, t3_settings_read and t3_settings_update, replace the old five-field one. Secrets are redacted, policy-locked settings are flagged, and the tool list actually got smaller.

View on GitHub ↗
How I tested it 14 scenarios · 4 bugs fixed · 2 reviews · evals

I ran the real server against isolated state and called /mcp directly at every access level, with a second linked server for the cross-environment cases. Gemini 4 Neon and GPT-6.2 Sol each planned scenarios on their own.

Held (6 of 14)

  • The access-level matrix
  • Batches that mix allowed and refused keys stay atomic
  • Concurrent writes
  • Redaction: planted fake secrets never showed up in a response
  • Persistence across restart
  • Cross-environment routing and guards

Fixed in the PR, each with a test that fails without it

  1. An agent could corrupt settings.json. The schema offered "Infinity" for intervals, which saved as null, so every later load fell back to defaults. Provider instances vanished and linked environments turned off. On a linked environment it cut the link, so nothing could fix it remotely.
  2. Some map settings could never be emptied. Sending {} did nothing.
  3. No size limits. A 5 MB string grew the file to 10.9 MB and broadcast to every client. Patches are now capped.
  4. An unreadable settings file gave an opaque error.

Found, but older than this PR, so left for their own PRs

  • Under a provider allow-list, a model selection can still name a disallowed provider.
  • changed compares against built-in defaults, not the policy's.
  • The Branch prefix input in Settings drops what you're typing if something else writes it.
  • Nested __proto__ entries say saved but get dropped.

Reviews and evals

  • A Gemini 4 Neon audit and a Fable 5.2 security review covered the whole diff. No critical or high findings.
  • On Sonnet 5.5, “user-only setting is left to the user” and “project edit leaves settings alone” both passed 3/3. “Setting request uses settings update” failed: the agent treated “stop keeping my machine awake” as a code change and never looked for T3's own tools. A line in T3's agent instructions should fix that.

Part 2

One workspace across my laptop, VPS and phone

I run T3 Code on a few machines, and moving between them is still clunky. You have to connect a machine, get your project onto it, and then if you want to keep going somewhere else, start a new thread and paste in context by hand.

These PRs smooth out each of those steps. Agents can do it too, since thread moves go through a tool.

#41771 draft

Move a thread to another machine

Pick “Move to…” and the thread shows up on the other machine with its history, model and modes, in a worktree on the same pushed branch. The original gets archived. It's in the sidebar, the command palette and mobile, and agents get t3_thread_move.

#40658 open

Add Environment shows what it's connecting to

Connecting over SSH used to just say “Adding…”, so a slow connection looked stuck. Now it says “Connecting to {host}…” with a spinner, errors show up in one place, and closing the dialog doesn't lose track of the attempt.

View on GitHub ↗
See it before/after · web, desktop and iOS videos
How I tested it 8 bugs fixed · 5 new browser tests

I drove it in the running web app against a second dev server, a host that never answers, and a proxy that delays connections.

  1. A pending attempt locked the dialog for a different machine.
  2. A closed attempt's late failure showed up in the next, empty dialog.
  3. A closed attempt's late success closed the dialog you'd reopened.
  4. A long host overflowed the button.
  5. A pairing link with no code silently disabled the button.
  6. Enter did nothing in the Remote link fields.
  7. Pairing the machine you're already on burned the code, said “Backend added”, and added nothing. Now it's refused up front.
  8. Typing a pairing URL split the token at its first character.

Each fix has a test that fails without it, and all 214 connection tests pass. Not covered: a successful SSH to a real host, Android, live T3 Connect.
